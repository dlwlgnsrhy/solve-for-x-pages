검증 가능한 샘플 데모 (가상 데이터)

ERP Ledger Kit

전표 자동화의 핵심은 숫자가 아니라 신뢰입니다. 3개 회계 시스템의 전표를 하나의 장부로 정규화하고, 차변·대변이 균형을 맞추는지, 이미 넣은 전표가 다시 들어가지 않는지를 샘플 데이터로 확인합니다 — 그리고 내 시스템의 전표 CSV를 직접 올려서도 확인합니다.

이 킷이 해결하는 문제

영림원·아마란스·SAP처럼 소스마다 형식이 다른 전표가 하나의 장부로 들어올 때, 불균형 전표나 중복 업로드는 장부를 깨뜨려 정산과 대장 점검에 시간을 쓰게 만듭니다. 이 킷은 3개 소스를 한 계약으로 정규화하고, 균형이 맞지 않는 전표는 장부에 들어오기 전에 차단합니다.

이 예시가 뭘 보여줍니까

100% 가상 데이터입니다. 가상의 회계 시스템 3곳에서 온 전표 5건(정상 4건 + 첫 전표 번호의 중복 재전송 1건)입니다. 아래는 균형 검증과 중복 전표가 거러나는 과정, 거른 전표의 실패 로그입니다.

1. 3개 소스의 전표 5건 입력

영림원·아마란스·SAP의 전표가 공통 계약(소스·전표번호·계정·차변·대변)으로 들어옵니다. 마지막 1건은 첫 전표의 번호가 다시 온 경우입니다.

입력 전표 (샘플 5건)
소스전표 번호계정
영림원YR:2026-0001매출-영림원
아마란스AM:2026-0001매출-아마란스
SAPS:2026-0001매출-SAP
아마란스AM:2026-0002매출-아마란스

2. 차변·대변 균형 검증

수락된 4건의 합을 다시 계산해 비교합니다 — 차변 합 = 대변 합 이므로 이 장부는 균형(balanced) 상태입니다.

3. 중복 전표 멱등 필터

이미 처리한 YR:2026-0001가 다시 들어오자 새 장부 행을 만들지 않고 실패 로그에 남겼습니다 — 다시 업로드해도 숫자가 두 번 들어가지 않습니다.

4. 재처리 시 멱등성

실패 기록 1건을 그대로 다시 보내면, 이미 처리된 전표이므로 새 반영 0건, 건너뜀 YR:2026-0001 로 SUCCEEDED — 결과가 번복되지 않습니다.

5. 직접 올린 파일로 확인

아래에 내 시스템에서 내보낸 전표 CSV를 올려보세요 — 소스명·전표번호·계정코드·차변·대변 열이 있으면 됩니다. 계정 코드는 내 파일에 등장하는 값 그대로 인식하며, 차·대변 균형과 중복 전표 여부를 브라우저 안에서 검증합니다. 샘플 입력 CSV를 내려받아 그대로 돌려도 됩니다.

CSV 파일을 여기에 놓거나

샘플 CSV 다운로드

이것이 주는 가치

  • 불균형 전표가 장부에 못 들어옵니다 — 합이 맞지 않으면 반영 전에 차단됩니다.
  • 재업로 해도 두 번 들어가지 않습니다 — 중복 전표는 거르고, 왜 거른지 로그에 남깁니다.
  • “무엇이 어긋났는지”가 숫자로 확인됩니다 — 재집계가 아니라 검증이 먼저입니다.

이 데모가 증명하지 않는 것

샘플 데이터와 메모리 기반 처리로 전표 정규화·균형·멱등 구조를 검증한 기술 데모입니다. 특정 ERP의 실데이터 연결, 인증, 처리량, 실제 회계 시스템과의 정합은 아직 검증하지 않았습니다.
