검증 가능한 샘플 데모 (가상 데이터)

Integration Reliability Kit

외부 시스템 연동은 정상 건만 처리하는 것으로 끝나지 않습니다. 일부 행이 실패해도 정상 행을 보존하고, 실패 원인을 남긴 뒤 수정된 한 건만 재처리해야 합니다 — 그리고 내 시스템의 실패 로그를 직접 올려 어떤 건을 다시 돌릴지 확인합니다.

이 킷이 해결하는 문제

ERP·API·파일 연동은 한 행만 잘못되어도 전체 배치 실패 후 처음부터 다시 넣거나, 다시 돌려서 중복이 생기는 구조로 끝나기 쉽습니다. 이 킷은 정상 행은 그대로 살리고, 깨진 행만 원인과 함께 분리해 수정된 행만 재처리하는 구조입니다.

이 예시가 뭘 보여줍니까

100% 가상 데이터입니다. 전표 3건(ERP·파일·API 각 1건) 중 파일 1건은 계정 매핑이 의도적으로 깨져 있습니다. 아래는 같은 3건을 최초 실행 → 수정 후 재처리 → 중복 재전송 순으로 돌린 결과입니다. 이 페이지의 모든 데이터는 샘플 데이터이지 견적이거나 실제 거래가 아닙니다.

2. 수정 후 수동 재처리

잘못된 계정 매핑을 수정한 한 건만 재처리했습니다. 상태는 완료, 실패했던 1건이 정상 처리되었습니다.

3. 중복 입력 보호

이미 처리한 외부 ID를 다시 보냈을 때 새 레코드를 만들지 않았습니다. 중복 키 ERP:INV-001를 건너뛰었습니다.

4. 적용 예시 (가상 데이터): 매출·재고 → BI 대시보드

POS 매출과 SCM 재고 이동 3건을 API 입력으로 정규화했습니다. 정상 2건은 보존하고, 매핑이 없는 SCM 1건만 실패 로그에 남긴 뒤 수정·재처리했습니다.

실제 시스템(POS, 재고관리 등)의 연결·증분 기준·대시보드 스키마는 계약 전 샘플 감사가 필요합니다. 이 샘플은 운영 처리량이나 고객 성과를 증명하지 않습니다.

5. Looker Studio용 CSV 출력

처리된 2건을 Looker Studio에 바로 넣을 수 있는 CSV(헤더 고정, BOM 無, 끝 줄바꿈)로 내보냅니다. 대시보드 파이프라인은 수동 작업 없이 이 파일에서 시작합니다.

6. 클라이언트용 실패 설명

기술 로그를 그대로 던지지 않습니다. 실패마다 사람이 읽을 수 있는 한 줄로 다시 씁니다 — 아래 1줄이 그 예입니다.

  • failure-2-unknown_account · UNKNOWN_ACCOUNT · 계정 코드 매핑을 확인해야 합니다. (retryable)

내 실패 로그로 확인

내 연동 시스템의 실패 로그 CSV를 올려보세요 — 외부 ID·실패 코드 열이 있으면 됩니다 (사유 열은 선택). 범용 어휘(타임아웃·5xx·429 등 / invalid·not_found·4xx 등)로 재처리 가능·불가·확인 필요로 분류하고, 내 시스템만의 코드는 “확인 필요”로 정직하게 분리합니다.샘플 입력 CSV를 내려받아 그대로 돌려도 됩니다.

이것이 주는 가치

  • 전량 재임포트 없음 — 100건 중 1건이 깨져도 99건은 그대로 보존됩니다.
  • 이중 반영 없음 — 중복 보호 덕분에 다시 돌려도 숫자가 두 번 들어가지 않습니다.
  • 실패마다 원인이 사람 말로 기록됩니다 — 추측이 아니라 확인하고 고칩니다.

이 데모가 증명하지 않는 것

샘플 데이터와 메모리 기반 처리로 복구 구조를 검증한 기술 데모입니다. 특정 ERP의 실데이터 연결, 고객 업무 성과, 운영 환경의 처리량은 아직 검증하지 않았습니다.
